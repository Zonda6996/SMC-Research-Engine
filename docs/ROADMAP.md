## Трек A — корректность движка

- [x] **A1. Развязать число сигналов от режима.** ✅ Реализовано.
  Проблема: safe/risk/standard берут ОДИН и тот же набор кандидатов, но число реальных входов
  разное (ONDO 15m 20k: safe **88** / risk **112** / standard **86** на 1658 кандидатах).
  Причина — кулдаун `blockedUntil = exitIndex + postExitBars` в `src/core/signals/ArrowTradeReplay.ts`:
  у risk стоп ближе → сделки короче → блокировка снимается раньше → влезает больше входов.
  У вендора режим почти не меняет число сигналов (±5-8). Следствие: сравнение safe vs risk
  сейчас НЕ «яблоки к яблокам» (разные N и разные наборы сделок).
  Варианты (⚠ решает автор): (а) единая режимо-независимая сетка допуска сигналов (кулдаун по
  фиксированной структуре/числу баров, не по exit конкретной сделки) → все режимы торгуют один
  набор, различаясь только управлением, как у вендора; (б) оставить, но всегда сравнивать режимы
  на общем наборе. НЕ менять без решения.
  **Диагностика (2026-08-13, ONDO 15m off, Binance-перп, 20k):** разрыв подтверждён как чисто
  кулдаунный — заморозка набора входов на safe роняет risk 112 → 88 (≈ вендор 89). Побочно:
  risk/off на ONDO по факту УБЫТОЧЕН (−4.44R, PF 0.91) — привлекательные risk-цифры были у
  фильтра slope + малая выборка (n=48). Чистого «референсного режима» с равным N нет:
  `replayArrowSignals` всегда доп. применяет свой кулдаун (frozen-on-safe → standard = 54).
  Лечение — РАЗДЕЛИТЬ допуск сигнала (режимо-независимый) и управление (per-mode). ⚠ Правило
  допуска выбирает автор: (а) фикс. спейсинг по барам; (б) допуск на уровне сигнала без
  exit-кулдауна; (в) канонический режим задаёт набор + отключить кулдаун в реплее этого набора.
  Раннер диагностики: `tmp/modeAdmissionProbe.ts`.
  **Резолюция (2026-08-13):** (в)-safe ОТПАЛ — наш safe-кулдаун выше вендора и гуляет по активам
  (BTC 96 / ETH 100 / ONDO 88 против вендора ~83-85). Вместо этого — вариант **(а): фиксированный
  шаг в БАРАХ**. Подтверждено: у вендора число стрелок ~85-90 не зависит ни от актива, ни от ТФ
  (BTC safe: 3m 85 / 15m 85 / 30m 85 / 1h 88 / 2h 90) → шаг именно в барах. `N≈180` баров матчит
  вендора по всем активам и ТФ (свип: `tmp/spacingSweep.ts`). Свип шага по перформансу
  (`tmp/stepPerfSweep.ts`): **шаг НЕ создаёт edge** — BTC/ETH отрицательны при любом N, ONDO слабо
  плюсовой при любом N. Поэтому N выбираем по верности/сравнимости (вендор-якорь 180), а НЕ по
  макс. Net R (это был бы оверфит на шуме ONDO).
  **Реализация A1 (согласовано направление):** режимо-независимый допуск (greedy min-spacing N=180
  баров) → все режимы управляют одним набором стрелок, каждая стрелка = независимая сделка (без
  exit-кулдауна). N — именованная константа (при нужде per-TF). Радиус: `replayArrowSignals` зовут
  бенчмарк/тесты/визуализатор → новый шаг допуска вживляем аккуратно, ядро реплея сохраняем, `tsc`+тесты.
  **Сделано (2026-08-13):** `ARROW_SIGNAL_SPACING_BARS = 180` + `admitArrowSignals()` (greedy min-spacing по
  барам) в `ArrowSignalEngine.ts`; `replayAdmittedArrowSignals()` (каждая стрелка = независимая сделка, без
  exit-кулдауна) в `ArrowTradeReplay.ts` — старый `replayArrowSignals` (per-mode кулдаун) сохранён для
  совместимости и тестов. Вживлено в визуализатор (`tools/visualizer/server.ts`) и бенчмарк
  (`tools/research/auditReversalBenchmark.ts`). `tsc` чист; тесты 503/505 (2 падения — отсутствующий
  `data/vendor-exports/bybit-btcusdt-perp-15m.csv`, не связано с A1). Проверка режимо-стабильности на реальных
  20k барах (`tmp/a1OndoReproduce.ts`): ONDO 15m — OLD safe 88/std 86/risk 112 → NEW 86/86/86; BTC 15m —
  OLD 96/100/121 → NEW 88/88/88 (admitted матчит вендор-плотность ~85-90).

## Трек B — research фильтров

- [ ] **B1. Бенчмарк-харнесс фильтров.**
  Матрица filter × asset × TF × mode с train/OOS сплитом, издержками, cluster-equal метрикой и
  отдельным long/short gate. Основа — `tools/research/auditReversalBenchmark.ts` (сейчас только
  off + contraction) + `evaluateFilterMode` из `tools/visualizer/server.ts`. Цель — одна таблица
  «где что работает» вместо ручного перебора в UI. Черновой headless-раннер: `tmp/reproFilters.ts`.

- [ ] **B2. Кросс-биржевая устойчивость (дешёвый OOS-прокси).**
  Наблюдение автора (2026-08-13, ONDO 15m, 20k баров): результат зависит от биржи — фитили
  (high/low) триггерят стопы/тейки по-разному, а объём меняет exhaustion/combo и OWN2-триггер.
  Замеры:

  | Биржа      | safe total/stop/tp/part | risk total/stop/tp/part |
  |------------|-------------------------|-------------------------|
  | Bybit      | 88 / 10 / 56 / 22       | 93 / 25 / 48 / 20       |
  | Bybit.P    | 86 / 7 / 55 / 24        | 91 / 19 / 50 / 22       |
  | Binance    | 90 / 12 / 52 / 26       | 98 / 21 / 51 / 26       |
  | Binance.P  | 83 / 9 / 50 / 24        | 89 / 22 / 45 / 22       |

  Идея: гонять конфиг по 3-4 площадкам. Выживает везде → доверия больше; живёт на одной →
  скорее шум/оверфит под микроструктуру площадки. Подтверждённый вывод → перенести каветат в
  `NEGATIVE-KNOWLEDGE.md`. ⚠ Требует, чтобы фетч умел выбирать биржу (сейчас фикс — Binance
  USDT-M futures, `market='futures'`).

- [ ] **B3. Кондиционирование под класс актива («подгонка» в хорошем смысле).**
