# Спецификация фильтров сигналов Arrow и сводка тестов (ARROW_FILTERS_SPEC)

Данный документ содержит полное техническое описание всех внедренных фильтров для сигнального движка **Arrow (Zonda Reversal / Apex)**, их механику, формулы, плюсы/минусы и результаты проведенных бэктестов. Предназначен для разработчиков, исследователей и других ИИ-агентов.

---

## 1. Общий контекст движка Arrow
Сигналы **Arrow** генерируются на основе конверта экстремумов ALMA (`ApexEngine.ts`) и направленного свечного анализа (`ArrowSignalEngine.ts`). 
* **Точка входа**: На закрытии свечи сигнала (`signalAt`).
* **Режимы исполнения (Replay)**: 
  * `SAFE`: Вход по close, короткий фиксированный стоп / быстрая частичная фиксация (Partial).
  * `RISK`: Вход по close, гибкий стоп за экстремум.
  * `STANDARD`: Классический режим с фиксированным соотношением Risk/Reward.

Без внешних фильтров базовый сигнал Arrow подвержен проблеме **"падающих ножей"** — входу в контртренд на сильном движении или при отсутствии реальной ликвидности.

## 2. Подробный разбор каждого фильтра

### 1. Фильтр Liquidity POI (Зоны ликвидности)
* **Файлы реализации**: `src/core/liquidity/LiquidityHeatmapEngine.ts`, `src/core/confirmation/LiquidityPoiCalibration.ts`.
* **Принцип работы**:
  Сигнал валидируется только в том случае, если тень (wick) свечи сигнала геометрически коснулась активной зоны ликвидности (**Liquidity POI**).
* **Механика и математика**:
  1. `LiquidityHeatmapEngine` рассчитывает профиль плотности лимитных ордеров (notional depth) по бинам цены.
  2. `LiquidityPoiCalibration` объединяет близкие пулы в динамические зоны с границами `[near, far]`.
  3. Для `Long` сигнала проверяется: `candle.low <= Math.max(zone.near, zone.far)`.
  4. Для `Short` сигнала проверяется: `candle.high >= Math.min(zone.near, zone.far)`.
  5. Учитываются только «живые» зоны (`knownAt <= signalAt` и `lifecycleState !== 'spent'`).
* **Плюсы**:
  * Отсекает до 50-60% хаотичных сигналов "в воздухе".
  * Кардинально улучшает винрейт и Net R на флэтовых и боковых активах (например, ONDO 30m с -8.30R превращается в +3.34R).
* **Минусы**:
  * **Слепое гео-касание**: Не учитывает, как именно цена отреагировала на зону (закрылась внутри или агрессивно отскочила).
  * Режет количество сделок, на сильных трендах может пропускать импульсные входы.

### 2. Фильтр Exhaustion (Истощение объема / Momentum)
* **Файлы реализации**: `src/core/signals/ArrowTradeReplay.ts`.
* **Принцип работы**:
  Фильтрует сигналы, появившиеся на аномально высоком относительном объеме (`relativeVolume >= 0.8`).
* **Механика**:
  * `relativeVolume` рассчитывается в `ArrowSignalEngine.ts` как отношение объема свечи к средней скользящей объема за 20 баров.
  * Если `relativeVolume >= 0.8`, считается, что на рынке идет пробойный импульс (breakout), а не истощение движения. Сигнал отбрасывается.
* **Плюсы**:
  * Защищает от входа "в лоб" агрессивному рыночному пробою.
* **Минусы**:
  * Иногда отсекает истинные институциональные кульминационные покупки/продажи (volume absorption), где высокий объем как раз означает разворот.

---

### 3. Фильтр Combo (Liquidity POI + Exhaustion)
* **Файлы реализации**: `src/core/signals/ArrowTradeReplay.ts`, `tools/visualizer/server.ts`.
* **Принцип работы**:
  Совмещает оба правила: **Касание активной зоны Liquidity POI** AND **relativeVolume < 0.8**.
* **Плюсы**:
  * Наиболее стабильный комбинированный фильтр. Дает минимальную просадку на большинстве таймфреймов и монетах.
  * Убирает как контртрендовый шум без уровня, так и пробойные импульсы на объемах.
* **Минусы**:
  * На некоторых парах (например, BTC 2h) оставляет не так много сделок, существенно сужая выборку.

---

### 4. Фильтр Плотности Пула (POI Stack Size / `stackShare`) — ⛔ ОТОЗВАН (look-ahead)
> **Не использовать.** `stackShare` нормирован на конец истории (утечка будущего); плюсы ниже — артефакт. Причинная проверка (`scratch/auditStackSizeCausal.ts`) показала, что порог не даёт прироста над обычным POI-касанием. Метрика годна только для UI. Детали — в разделе 4 «Главные выводы», пункт 2.
* **Файлы реализации**: `scratch/auditStackSize.ts`, `src/core/confirmation/LiquidityPoiCalibration.ts`.
* **Принцип работы**:
  Развитие фильтра Liquidity POI. Требует касания не просто любой зоны, а зоны с плотностью (объемом ордеров) не ниже заданного порога от максимальной зоны на графике (`stackShare >= minStack`).
* **Механика**:
  * Каждый POI получает метрику `stackShare = stackNotional / maxStackNotional`, где `maxStackNotional` — максимальная масса ордеров среди всех активных зон этого направления.
  * Тестировались пороги: `0%` (любая), `10%`, `20%`, `30%`.
* **Плюсы**:
  * Игнорирует мелкие, слабые полки ордеров, которые цена easily прошивает.
  * На ONDO 30m фильтр `stackShare >= 20%` поддал профит с **+3.34R** до **+5.20R** (отсеял всего 1 ложный сигнал, сэкономив 2R).
  * На ETH 30m вывел результат из **-0.96R** в **+0.86R** (при `≥ 30%`).
* **Минусы**:
  * На крупных активах (BTC) дает эффект, схожий с фильтром `Combo`, не создавая принципиального прорыва за пределы `Combo`.

## 4. Главные выводы и текущие гипотезы

1. **Базовый фильтр POI критически необходим**: Без него сигналы Arrow на большинстве таймфреймов сливные (от -8R до -15R). Подключение POI сразу режет просадку в 2-3 раза или выводит в плюс.
2. **⛔ ОТОЗВАНО (look-ahead): «Плотность (Stack Size) помогает на альтах».** Прежний вывод (ONDO 30m +5.20R, ETH 30m +0.86R при `stackShare >= 20-30%`) оказался артефактом утечки будущего. `stackShare` нормируется движком на сильнейший активный стек **на конец истории**, поэтому порог использовал информацию, недоступную на момент сигнала. При причинной нормировке (знаменатель = сильнейший стек, известный на `signalAt`) прирост исчезает: ONDO 30m возвращается к +3.30R (= уровню обычного POI-касания, порог ничего не добавляет), ETH 30m ≈ −0.10R (не +0.88R). Проверено скриптом `scratch/auditStackSizeCausal.ts` (колонки leaky vs causal). Вывод: `stackShare` — только UI-метрика; как торговый/бэктест-фильтр непригодна. Реален лишь сам POI-touch (`off → ≥0%`), и он снижает просадку, но не создаёт положительного ожидания.
3. **Геометрическое касание исчерпало потенциал**: Простое проверке "коснулась ли тень зоны" уже дала всё, что могла. Следующий шаг для качественного прыжка — проверка **качества отскока / Rejection (Отклонение)**:
   * Проверка длины тени свечи (rejection tail).
   * Проверка закрытия свечи **снаружи** зоны (цена удержалась и отскочила, а не увязла внутри).
