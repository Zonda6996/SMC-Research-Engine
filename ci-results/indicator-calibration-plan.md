# План наблюдаемой калибровки Zonda Apex / Zonda Reversal

Дата: 2026-07-30
Статус: подготовка измерений; текущие формулы не меняются.

## Что реально есть в коде

### Apex

Текущая реализация `src/core/signals/ApexEngine.ts`:

- mean: `ALMA(hlc3, 200, 0.85, 6)`;
- границы: `mean × exp(±k×s)`, `k=5.6/9.6`;
- `s`: `ALMA(TR/close, 122, 0.625, 3.5)`;
- это аппроксимация по наблюдаемым точкам, не восстановленная vendor formula.

Известный контроль:

- mean переносился на внешние BTC 15m / ETH 1h с ошибкой около 0.024% / 0.269%;
- ошибка ширины на этих точках была примерно 7.8% / 2.8% для принятого варианта в старом отчёте;
- пользователь видит абсолютное расхождение BTC около $20–100 ниже 4h и $100–250 на 4h+;
- absolute USD error нельзя смешивать с spot/futures basis и относительной ошибкой ширины.

### Reversal

Текущая модель:

1. край Apex взводит сторону;
2. BUY только на bullish candle, SELL только на bearish candle;
3. re-arm у средней.

Это минимальное приближение. Оно не содержит подтверждённой полной логики «страха и жадности». Все 14 прошлых trigger-family гипотез дали отрицательный net baseline после costs; Safe/Standard/Risk не маппируются.

## Нужные TV-замеры Apex

Для каждой точки нужен один и тот же закрытый бар и значения из status line, не по пикселям:

| Поле | Что записать |
|---|---|
| Symbol/feed | например `BINANCE:BTCUSDT` spot или perpetual futures |
| TF | 5m / 15m / 1h / 4h |
| Timestamp | точное время бара + timezone TradingView |
| OHLC | open/high/low/close этого бара |
| Mean | значение средней Apex |
| Upper inner / outer | обе верхние линии |
| Lower inner / outer | обе нижние линии |
| Inputs | source, lookback, inner multiplier, outer amplitude |
| Screenshot | весь график + status line + symbol/feed + TF |

Минимальный набор первой итерации:

- BTC spot: 3 даты × 5m/15m/1h/4h = 12 точек;
- BTC perpetual: те же timestamps = ещё 12 точек для отделения basis;
- ETH или SOL: 1–2 OOS даты × четыре TF, которые не участвуют в подборе.

Правило отбора до просмотра OOS:

1. Ошибка mean и ошибка ширины считаются отдельно.
2. Для ширины сравнивается безразмерное `s`, восстановленное из каждой линии через логарифм.
3. Выбирать плато параметров, а не лучший одиночный пик.
4. Порог и candidate family фиксировать на train-точках до OOS.
5. Не менять канонические defaults, пока один вариант не переносится по TF, датам и второму символу.

## Нужные наблюдения Reversal

Для каждого BUY/SELL и нескольких случаев без сигнала:

- symbol/feed, TF, timestamp, Risk Mode;
- screenshot минимум 20–30 баров до и 10 после;
- OHLC сигнальной свечи и соседних свечей;
- значения всех линий Apex на этих барах;
- был ли edge touch на текущем или предыдущем баре;
- положение цены относительно mean;
- предыдущий Reversal той же и противоположной стороны;
- если возможно, видимое значение/цвет/состояние fear-and-greed блока;
- отдельно 5–10 «почти таких же» случаев, где сигнала НЕ было.

Первая проверяемая задача — не прибыльность, а классификация события: какие наблюдаемые признаки отличают signal от matched no-signal. Только после устойчивого OOS-классификатора можно тестировать Reversal изолированно или как confluence POI.

## Что не делать

- не считать совпадение одного скрина восстановлением формулы;
- не подгонять ширину Apex в долларах только на BTC;
- не принимать визуальное совпадение без status-line чисел;
- не исследовать торговый edge до проверки event reconstruction;
- не называть Reversal самостоятельной прибыльной системой без train/test, costs, multi-asset и tail robustness.
